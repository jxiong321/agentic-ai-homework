  The Part 0 algorithm I designed
  I want to use the following approach.
  Initialize:
  - A dictionary model_calls to store unique message IDs and their prompt
  sizes.
  - A set tool_call_ids to track distinct tool invocations.
  - first_call and last_call variables initialized to None.
  - Running totals for prompt tokens and cache-read tokens.
  Then iterate through the JSONL records.
  For every assistant record:
  1. Extract the model call's message.id.
  2. If the ID hasn't appeared before, calculate its prompt size by adding
  input, cache-read, and cache-creation tokens.
  3. Store that prompt size in model_calls, keyed by message ID.
  4. Increment the total prompt-token count and total cache-read count.
  5. If first_call is None, assign it the current message ID.
  6. Update last_call to the current message ID.
  7. Independently examine tool-use blocks and add unique tool-use IDs to
  tool_call_ids, even when an assistant record's message ID has already
  appeared.
  After processing all records, calculate:
  - model_calls: number of distinct model IDs.
  - tool_calls: number of distinct tool-use IDs.
  - prompt_tokens: cumulative prompt tokens.
  - cache_read_tokens: cumulative cache-read tokens.
  - cache_read_share: cache reads divided by total prompt tokens.
  - first_prompt: prompt size for first_call.
  - last_prompt: prompt size for last_call.
  - cumulative_over_first: total prompt tokens divided by first prompt size.

  behind it.

  How the loop works (agent/loop.py)

  Each pass through the loop does five things:

  1. Check the bounds, before every model call, in this order:
     - steps used reached max_steps → turn_limit
     - client.total_tokens reached max_tokens → token_budget
     - elapsed time reached wall_clock_s → wall_clock

     Checking before the call is what the checker expects: exactly N calls for
     the turn limit, and no new call once the budget is reached. The order only
     matters when two bounds trip at the same moment.
  2. Call the model, write trace.model_call(step, response), and append
     response.assistant_message() unchanged.
  3. Stop if the model is done. A refusal stop reason ends the run with refusal.
     A response with no tool calls ends it with model_stopped.
  4. Run each requested tool, write trace.tool_call, and send all the step's
     results back as one user turn of tool_result blocks.
  5. Return the last text. Every exit calls trace.end exactly once and then
     returns, so a second call can't happen.

  The control-flow choices worth reviewing:
  - Tool errors are split into two kinds, following the registry's design in
    tools/init.py (tools/__init__.py). A result with is_error (bad input, issue
    not found) goes back to the model so it can recover. A tool that raises an
    exception ends the run with tool_error. The alternative, ending on any
    is_error, would kill runs the model could easily fix.
  - "Last text" is the most recent non-empty text, not the final response's
    text, which is often empty because that response was only a tool call.
  - max_tokens and pause_turn stop reasons count as model_stopped when the
    response contains no tool calls.
  - Known limitation: the wall clock can't interrupt a call that is already
    running. One slow model call can overshoot 180 s by that call's latency. The
    checker's 0.2 s calls can't show this, but a stalled Gemini request could.

  What I wrote

  ways/direct.py is one model call with no tools. It goes:
  1. read_issue at step 0.
  2. One model call with the issue and the repo summary, traced as step 1.
  3. Parse the reply with parse_triage_comment, rebuild it with
     format_triage_comment, and post it at step 1.

  ways/workflow.py is a fixed sequence with exactly two model calls, split into
  reusable functions for Part D:
  - gather(ctx): read the issue → model call 1 asks for search terms →
    search_repo once per term. It returns the issue text and the combined search
    results.
  - choose(ctx, issue, search_results): model call 2 picks the label and file,
    and it returns them parsed.
  - run(ctx): gather → choose → post.

  Keeping choose separate from posting lets the Part D hybrid look at the
  workflow's answer, and decide whether to hand off to the agent, before
  anything is posted.

  eval/check_triage.py reads only tracker.comments(run_id=..., issue=...). It
  requires exactly one comment, then compares the parsed label and file with the
  answer, normalized with normalize_path. Nothing the model said is consulted.

  Prompts: prompts/direct.md, prompts/workflow_extract.md and
  prompts/workflow_choose.md. Each puts the label definitions from FORMATS.md
  before the exact two-line reply format, and treats the issue as untrusted
  data.

  Design decisions to review

  - Up to 3 search terms, one search each. The handout's sequence says
    "search_repo" once. I allowed 1–3 terms because a single literal search
    often misses. The order is still fixed and the model never chooses a tool.
    The alternative, exactly one search, is simpler but more brittle.
  - The workflow does not get the repo summary. The handout gives it only to the
    direct call, and leaving it out keeps the workflow's answer based on what
    it actually searched. Adding it would probably raise accuracy but blur the
    comparison. This is your call.
  - An unparseable reply is still posted, as label: unknown, so it counts as a
    failure in the tracker rather than a crash.
  - No system prompt. Each prompt goes in as the single user message, with
    {issue} / {repo_summary} / {search_results} filled in.
